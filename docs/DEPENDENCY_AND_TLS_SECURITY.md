## 1. TLS Certificate Interception: Root Cause Analysis

During Phase 1, `npm install` encountered `UNABLE_TO_VERIFY_LEAF_SIGNATURE` errors when communicating with the npm registry. A temporary workaround (`strict-ssl=false`) was placed in `.npmrc`.

In Phase 2, an independent investigation was conducted to determine the root cause:
- **Root Cause Identified:** Avast Antivirus running on the host machine has "Avast Web/Mail Shield" active.
- **Mechanism:** The shield intercepts all outbound TLS/HTTPS connections on port 443 and dynamically re-signs server certificates using a local self-signed Root Certificate Authority:
  - **Subject:** `CN=Avast Web/Mail Shield Root, O=Avast Web/Mail Shield, OU=generated by Avast Antivirus for SSL/TLS scanning`
  - **Issuer:** `CN=Avast Web/Mail Shield Root, O=Avast Web/Mail Shield, OU=generated by Avast Antivirus for SSL/TLS scanning`
  - **SHA-256 Fingerprint:** `6C:47:EA:72:A4:98:F7:48:BF:D3:04:1B:4D:A3:E1:3D:DB:62:B7:B7:35:8A:44:08:39:DB:15:A4:0D:FE:77:D5`
  - **Validity:** Valid until `Jan 1 12:00:00 2040 GMT`
- **Why Node.js Fails by Default:** While Windows browsers and OS utilities trust this CA via `Cert:\LocalMachine\Root`, Node.js ships with its own static Mozilla root certificate store and does not read the Windows certificate store by default.

---

## 2. Permanent Secure Remediation

To eliminate the security risks of `strict-ssl=false` (which completely disables TLS certificate validation and makes package fetches vulnerable to MITM attacks), the following permanent architectural fix was implemented:

1. **CA Extraction:** The local Avast Root CA certificate was extracted from the Windows Certificate Store (`Cert:\LocalMachine\Root`) and exported to a standard PEM bundle:
   `F:\Dev_Workspace\Cache\avast_root.pem`
2. **Project `.npmrc` Hardening:** Configured `.npmrc` exclusively within the project root:
   ```ini
   cache=F:/Dev_Workspace/Cache/npm
   cafile=F:/Dev_Workspace/Cache/avast_root.pem
   strict-ssl=true
   audit=false
   fund=false
   ```
3. **Outcome:** Full cryptographic certificate chain verification is enforced on every connection (`strict-ssl=true`). The client verifies that remote endpoints possess valid certificates signed by either standard public CAs or the verified local Avast root.

## 3. Dependency Supply Chain & Native Bindings Audit

### 3.1 Installation with `--ignore-scripts`
- `package-lock.json` comprises 1098 packages.
- Dependencies were installed using `--ignore-scripts` to mitigate supply chain threats from arbitrary post-install script execution.
- **Native Modules Reviewed:**
  - `re2`: Optional native regular expression module. Because the host lacks C++ Build Tools (`cl.exe`), native compilation is skipped cleanly; fallback JavaScript regex engines are used with zero functional regression.
  - `esbuild`: Pre-compiled Windows x64 binary (`@esbuild/win32-x64`) executes directly without requiring local C++ compilation.
  - `drizzle-orm` & `express`: Pure JavaScript/TypeScript modules with zero native compilation dependencies.

### 3.2 Node 24 Runtime Compatibility
- Host Node.js version is `v24.13.0`.
- `superstatic@9.2.0` (transitive dependency of `firebase-tools`) specifies engine range `^18 || ^20 || ^22`.
- In OmniFlow local runtime, `superstatic` is not invoked. All local hosting and API routes are served directly by Express and Vite. Zero runtime or build anomalies were detected.
