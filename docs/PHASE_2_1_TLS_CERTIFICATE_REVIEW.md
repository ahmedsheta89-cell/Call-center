## 1. Executive Summary & Context

During Phase 2 dependency restoration, `npm install` and Node.js network operations encountered the TLS error `UNABLE_TO_VERIFY_LEAF_SIGNATURE` when attempting to contact `registry.npmjs.org` over port 443 (HTTPS).

Investigation revealed that Avast Antivirus Web Shield is active on the host machine. Avast inspects outbound HTTPS traffic by acting as a transparent TLS proxy (MITM), dynamically intercepting SSL/TLS handshakes, generating intermediate server certificates signed by its local Root Certificate Authority (CA), and injecting them into local socket streams.

To allow npm and Node.js to function securely without disabling SSL verification (`rejectUnauthorized=true` / `strict-ssl=true`), the Avast Root Certificate was extracted from the Windows Certificate Store and placed into `F:\Dev_Workspace\Cache\avast_root.pem`, configured via `.npmrc`.

This document presents the independent security audit, cryptographic fingerprint verification, trust boundary assessment, and portability guidelines for this certificate.

## 3. Threat Model & Trust Boundary Analysis

### 3.1 Mechanism of Interception (TLS MITM)
When an application initiates an outbound TLS handshake on port 443:
1. Avast Web Shield transparently intercepts the TCP SYN/ACK to remote hosts.
2. Avast establishes a real TLS session with the remote destination (e.g., `registry.npmjs.org`), validates the remote certificate against public CAs, and inspects the payload for malware/signatures.
3. Simultaneously, Avast establishes a local TLS session with the local client (Node.js/npm), presenting a dynamically generated server certificate signed by `CN=Avast Web/Mail Root`.
4. Because Node.js ships with its own hardcoded root store (Mozilla NSS roots) and ignores the Windows Certificate Store by default, Node.js terminates the connection with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`.

### 3.2 Security Implications & Risks
1. **Risk of Arbitrary Decryption:** Anyone possessing the private key corresponding to `CN=Avast Web/Mail Root` can decrypt all HTTPS traffic routed through this proxy.
2. **Local Machine Scope:** The private key resides in Windows DPAPI / Protected Storage managed exclusively by the Avast kernel driver on this specific machine.
3. **No Network Exposure:** The root certificate is self-signed and unique to this specific Avast installation or vendor version. Remote attackers cannot forge this signature unless they compromise the local machine's protected storage.
4. **Preservation of Strict SSL:** By configuring `cafile=F:/Dev_Workspace/Cache/avast_root.pem` alongside `strict-ssl=true` in `.npmrc`, we ensure that:
   - Node.js / npm still enforces certificate validation.
   - Any certificate NOT signed by this trusted local Avast root will be rejected.
   - We did **NOT** use `NODE_TLS_REJECT_UNAUTHORIZED=0` or `strict-ssl=false`, which would have completely compromised transport security.

## 4. Portability Assessment & Multi-Environment Rules

### 4.1 Machine-Specific Dependency
> [!IMPORTANT]
> The configuration `cafile=F:/Dev_Workspace/Cache/avast_root.pem` in `.npmrc` is **strictly machine-specific** to this development workstation.

- **On This Workstation (`FAWZY SHETA`):** Required because Avast intercepts port 443. Without `cafile`, npm commands fail.
- **On Standard Windows / Linux / macOS Machines (Without Avast):** Not required. Standard Node.js bundled CAs validate `registry.npmjs.org` directly.
- **On CI/CD Pipelines (GitHub Actions / GitLab CI):** `avast_root.pem` MUST NOT be referenced or trusted. CI/CD runners must use standard Mozilla/NSS public root stores.

### 4.2 Portability Architecture & Best Practices
To ensure repository portability across diverse development environments:
1. **Git Tracking:** `F:\Dev_Workspace\Cache\avast_root.pem` is located outside the Git repository in the isolated cache root (`F:\Dev_Workspace\Cache\`). It is NOT committed to Git.
2. **Local `.npmrc`:** If committed, `.npmrc` with a hardcoded Windows path `F:/Dev_Workspace/Cache/...` will break on Linux/Mac or other developers' machines.
   - *Recommendation:* Add `.npmrc` to `.gitignore` or use environment-level configuration `npm config set cafile "..." --location=user` so the repository remains clean of workstation-specific paths.
3. **Environment Detection:** Runtime scripts should check if `NODE_EXTRA_CA_CERTS` is needed dynamically rather than hardcoding static paths in project configuration.
